# Go AppHost Authoring

Patterns for editing `apphost.go`. Go AppHosts need **Aspire 17.0 or later** and Go 1.26 or
later on `PATH` (https://go.dev/dl/). **Never edit `.aspire/modules/`** - it is generated and
any change is clobbered. On older Aspire versions keep the AppHost in C# or TypeScript.

> Look up unfamiliar API: `aspire docs api search <query> --language go`
> then `aspire docs api get <id>`. If the search finds nothing, find the signature in the
> generated SDK instead of guessing: `grep -n "AddGoApp" .aspire/modules/aspire.go` (read-only).

## Detect and Scaffold

A Go AppHost is an `apphost.go` next to an `aspire.config.json` whose `appHost.language` is
`go`, plus a `go.mod` in that AppHost directory with
`replace apphost/modules/aspire => ./.aspire/modules`. Resolve `appHost.path` relative to
that configuration file, not the repository root. A Go
*service* inside a C# or TypeScript AppHost does **not** make that AppHost a Go AppHost: keep
authoring `apphost.cs` / `apphost.mts` and wire the service with `AddGoApp` (see
`apphost-wiring.md`).

| Goal | Command |
|------|---------|
| Go API + Redis starter | `aspire new aspire-go-starter` |
| Empty Go AppHost | `aspire new aspire-go-empty` |
| Add an AppHost to an existing repo | `aspire init --language go` |

## Hard Refusal: `.aspire/modules/` Is Off-Limits

`.aspire/modules/` (`aspire.go`, `base.go`, `transport.go`, `go.mod`) is the generated Go SDK.
`aspire add`, `aspire restore`, and `aspire run` / `aspire start` regenerate it, so hand edits
are lost. If asked to edit it - however the request is phrased - refuse and redirect:

```text
I won't edit files in .aspire/modules/ - that directory is generated by the Aspire CLI and
any edits are overwritten on the next `aspire add` / `aspire restore` / `aspire start`.
Make the change in apphost.go instead. To add an integration, run
`aspire add <integration>` and Aspire regenerates the SDK.
```

## Skeleton

Copied from `aspire new aspire-go-starter`:

```go
package main

import (
	"log"

	"apphost/modules/aspire"
)

func main() {
	builder, err := aspire.CreateBuilder()
	if err != nil {
		log.Fatal(aspire.FormatError(err))
	}

	// A Redis cache the API will use for read-through caching.
	cache := builder.AddRedis("cache")

	// The Go HTTP API. WithModTidy runs "go mod tidy" before launching so that
	// go.sum is always up to date. Aspire injects:
	//   - "ConnectionStrings__cache" so the API can dial Redis.
	//   - "OTEL_EXPORTER_OTLP_*" env vars (via WithOtlpExporter) so traces,
	//     metrics, and logs flow to the Aspire dashboard.
	api := builder.AddGoApp("api", "./api").
		WithModTidy().
		WithReference(cache).
		WaitFor(cache).
		WithHttpEndpoint(aspire.HttpEndpointEnv("PORT")).
		WithExternalHttpEndpoints().
		WithOtlpExporter()

	app, err := builder.Build()
	if err != nil {
		log.Fatal(aspire.FormatError(err))
	}
	if err := app.Run(); err != nil {
		log.Fatal(aspire.FormatError(err))
	}
}
```

## Handles and Deferred Errors

`Add*` and `With*` calls do not return `(value, error)`. They return a handle and record a
failure on it:

- The first error wins and later calls on a failed handle short-circuit. Read it with `Err()`.
- `Build()` returns `(app, error)` and short-circuits on any error recorded by a handle of its
  client, so a failed `Add*` or `With*` surfaces there even if you never read its `Err()`. Call
  `Err()` on a handle only to localize a failure sooner. `Run()` returns `error`; check both.
- Print errors with `aspire.FormatError(err)`: it expands `*aspire.CapabilityError` (message,
  code, capability, parameter details) and falls back to `err.Error()`. Use `errors.As` for the
  pieces:

```go
var capErr *aspire.CapabilityError
if errors.As(err, &capErr) {
	log.Printf("capability %s failed: %s", capErr.Capability(), capErr.Message())
}
```

## Options Structs

Required parameters are positional. Optional parameters are variadic functional options:
each method takes `options ...<Method>Option`, and each option is a typed value, so ordinary
calls need no pointers.

```go
api := builder.AddGoApp("api", "./api",
	aspire.AddGoAppPackagePath("./cmd/server"),
	aspire.AddGoAppBuildTags([]string{"netgo"}),
	aspire.AddGoAppRaceDetector(true)).
	WithModTidy().
	WithHttpEndpoint(aspire.HttpEndpointPort(8080), aspire.HttpEndpointEnv("PORT")).
	WithHttpHealthCheck(aspire.HttpHealthCheckPath("/health"))
```

- Option value names are generated from the method and parameter, such as
  `AddGoAppPackagePath`, `HttpEndpointEnv`, and `HttpHealthCheckPath`. Their underlying types
  are plain `string`, `int`, `bool`, or `[]string`. Some drop the method prefix
  (`GoPrivateTokenSecretId`), so confirm names in `.aspire/modules/aspire.go`.
- A pointer to the `<Method>Options` struct (`&aspire.AddGoAppOptions{...}`) is also accepted.
  Its scalar fields are pointers (`*string`, `*int`, `*bool`); build them with
  `aspire.StringPtr`, `aspire.IntPtr`, `aspire.BoolPtr`. Prefer option values.
- Whole DTO parameters stay pointers: see `WithDelveServer` below.
## Go Apps: `AddGoApp`

`AddGoApp(name, appDirectory, options...)` comes from `Aspire.Hosting.Go`. It was introduced
as a **preview package in Aspire 13.4** for C# and TypeScript AppHosts; its first stable
release is part of **Aspire 17.0**, alongside Go AppHost GA. Do not assume a stable 13.x
package exists. On 13.x, discover a compatible preview and obtain approval before adding
it with `aspire add go --version <compatible-preview-version>`; never change the AppHost's
release family or channel implicitly. Go AppHosts themselves need 17.0.

- `appDirectory` is relative to the AppHost directory. It is the Go module root (where `go.mod`
  lives) and the Docker build context for `aspire publish`, which generates a Dockerfile unless
  `appDirectory` already has one.
- `AddGoAppPackagePath` (default `.`) selects the main package, for example `./cmd/server`.
  Other options: `AddGoAppBuildTags`, `AddGoAppLdFlags`, `AddGoAppGcFlags`, `AddGoAppRaceDetector`.
- An existing Dockerfile is used unchanged: `PackagePath` does not rewrite its build command
  or entrypoint. Publishing a non-default package with an existing Dockerfile warns; verify
  that file builds and starts the intended package. Generated Dockerfiles honor
  `PackagePath`, build tags, linker flags, and compiler flags, but omit the race detector
  because they build with `CGO_ENABLED=0`.
- It already requires `go` on `PATH`, enables the OTLP exporter, and adds VS Code debugging.
- `WithModTidy()` (the scaffold default), `WithModDownload()`, and `WithModVendor()` run
  `go mod tidy`, `go mod download`, and `go mod vendor` before the app starts; `WithVetTool()`
  runs `go vet ./...`. All four apply in run mode only. Tidy actually uses
  `go mod tidy -e` and can modify the service's `go.mod` and `go.sum` even when downloads
  fail; inspect setup-resource logs and module diffs instead of treating its success as
  proof that dependencies resolved. Preserve the user's existing dependency workflow.
- The service reads its configuration from the environment. For example, `WithReference(cache)`
  on a Redis resource injects `ConnectionStrings__cache`, and `aspire.HttpEndpointEnv("PORT")`
  on `WithHttpEndpoint` puts the assigned port in `PORT`.

### Private modules and Delve

- `WithGoPrivate(privatePatterns, authHost, usernameArgName?, tokenSecretId?)` sets
  `GOPRIVATE` and wires credentials for private module hosts. Pass the token through a
  secret parameter; never hard-code it.
- `WithDelveServer(options...)` runs the app under
  `dlv --headless --listen=127.0.0.1:<port> --api-version=2 debug .` for remote debugging.
  With no arguments it uses the defaults. To configure it, wrap a `*DelveServerOptions` in
  `aspire.DelveServerOptions2`:

  ```go
  builder.AddGoApp("svc", "./svc").
  	WithDelveServer(aspire.DelveServerOptions2(&aspire.DelveServerOptions{
  		Port: aspire.IntPtr(2345),
  	}))
  ```

  `DelveServerOptions` fields are all optional pointers: `Port` (`*int`, default 2345),
  `AcceptMultiClient`, `ContinueOnStart`, `Log` (`*bool`, default false), `LogOutput`
  (`*string`), and `OnlySameUser` (`*bool`, unset uses Delve's default policy). Repeated calls
  are idempotent. It replaces the command line and needs `dlv` on `PATH`.- VS Code debugging of Go services is automatic through the Go extension (dlv-dap). Local
  launches keep symbols so breakpoints work.
- Go 1.26 and earlier on macOS and Windows ignore `SSL_CERT_FILE` / `SSL_CERT_DIR`, so
  custom certificate trust for the service relies on the system store there.

## Packages and the Generated SDK

`AddGoApp`, `AddRedis`, and every other integration method exist in `.aspire/modules/` only
after their package is added:

```bash
aspire add go      # Aspire.Hosting.Go; the name is the package id without "Aspire.Hosting."
aspire add redis
aspire restore --apphost apphost.go
```

`aspire add` records the package under `packages` in `aspire.config.json` and regenerates the
SDK. The 17.0 Go empty/init scaffold already includes `Aspire.Hosting.Go`; the starter also
includes Redis. Inspect the existing package list before adding anything.
`aspire restore` regenerates it from that file: run it after cloning, switching branches,
hand-editing `packages`, and in CI before `go build` / `go vet`. Without `.aspire/modules/`, Go
fails with `replacement directory ./.aspire/modules does not exist`. `.aspire/` is gitignored.

## Run and Validate

In Aspire 17.0+, `aspire doctor --format Json` checks the selected Go AppHost's toolchain.
It reports a missing `go`, an insufficient version, or an inconclusive/toolchain-switching
warning. Go 1.26+ is the straightforward supported setup. With Go 1.21-1.25, the outcome
depends on effective `GOTOOLCHAIN`: `local` fails; automatic downloads or PATH-only
switching produce warnings, not proof that the required toolchain is available.

```bash
aspire restore --apphost apphost.go    # regenerate the SDK
go vet .                               # compile-check apphost.go against it
aspire start --non-interactive --format Json
aspire wait <resource-name>            # repeat per resource
aspire describe --format Json --include-hidden
aspire stop
```

Never start the AppHost with `go run .`. `aspire.CreateBuilder()` needs the
`REMOTE_APP_HOST_SOCKET_PATH` variable that only the Aspire CLI sets, so it fails with
"REMOTE_APP_HOST_SOCKET_PATH environment variable not set". See `validation.md` for the full
flow and the hand-off to `aspire-orchestration`.

Debugging the Go AppHost itself requires a VS Code Aspire extension that advertises
`go-apphost.v1` and the Go debug adapter. An older extension that only debugs Go services
is not sufficient; ordinary CLI execution still uses `go run .` through Aspire.

## Hard Rules

1. Edit `apphost.go` only; never `.aspire/modules/`.
2. Always check the errors from `Build()` and `Run()`; use `Err()` on a handle only to localize a failure.
3. Run the AppHost with `aspire start --non-interactive` or `aspire run`, never `go run .`.
4. Prefer first-party `AddGoApp` (`Aspire.Hosting.Go`): preview from 13.4, stable from 17.0.
   Never opt a 13.x project into preview packages without approval.
5. Pass optional parameters as typed option values, such as `aspire.HttpEndpointEnv("PORT")`.
6. Look up any method you have not seen (API search, then the generated SDK); do not guess names.
