# Development

Use Node.js 22 or later, Git, and GitHub CLI. Create feature branches from `dev`
and target contributor PRs at `dev`. Before opening a PR, run:

```powershell
npm ci --ignore-scripts
npm test
```

See [CONTRIBUTING.md](../CONTRIBUTING.md) for skill formatting and agent-host checks.
Dev retains `CHANGELOG.md` and generated `opencode/` catalogs. Regenerate catalogs
with `npm run catalog` after changing shipped skills, references, or assets,
and commit them with the source changes. Run `npm run catalog:check` to check
the committed tree. CI rejects missing, extra, or stale V1 and V2 catalog files.
Feature PRs update the current version's changelog notes and preserve earlier
entries and the coordinated version.

The **OpenCode catalog check** runs on every PR, including stacked PRs, on
main/dev/release pushes, and on merge-queue candidates.

The **Release branch check** fails any PR into main unless its head is a
`release/<version>` branch in this repository.

## Expected release flow

1. **Cut the release.** Create `release/<version>` at the chosen dev commit.
2. **Advance dev.** Create `bump-dev/<next-version>` from current dev, run
   `npm run version:dev -- <next-version>`, and open a PR to dev. The command
   updates coordinated versions, adds the new changelog heading without changing
   existing entries, and regenerates catalogs.
3. **Prepare the candidate.** Backport needed fixes, finalize the changelog,
   regenerate catalogs with `npm run catalog`, and run `npm test`.
4. **Release to main.** Open the release PR to main. Maintainers approve and
   merge it; the publisher tags the exact merged commit, creates the GitHub
   release, and uploads the skills bundle.
5. **Merge back to dev.** Create `backport/pr-<release-pr>-to-dev` from current
   dev and merge main into it. Keep dev's next version and newer work, preserve
   non-version manifest changes and dev's current changelog entry, update earlier
   entries from main's approved changelog, and regenerate catalogs. Open a PR to dev
   and merge it with a merge commit.

## Publication

`.github/workflows/publish.yml` runs when a same-repository `release/*` PR
merges into main. It uses the event's `merge_commit_sha`, builds and attests
both bundles, and uploads only `aspire-skills-v<version>.tgz`.

Publishing uses `GITHUB_TOKEN`; no repo bot or stored automation credentials
are needed. Maintainers create PRs and approve merges. Tags and releases are
published in the same run because workflow-token tag pushes do not trigger
another workflow. Reruns must preserve the tag's commit and approved notes.

## Release-driven Aspire updates

The workflow starts directly on `release: published`. The release tag and
tagged commit supply the version and source identity; publication does not
dispatch the workflow or pass manual inputs.

The agentic workflow is authored in `.github/workflows/update-aspire.md` and
compiled with GitHub Agentic Workflows. It lives in this repository, but
`microsoft/aspire` is the editing workspace and PR destination.

GitHub does not start release-event workflows for releases created with
`GITHUB_TOKEN`. The current publisher and its credentials are unchanged, so
those automated releases will not start this workflow. It runs for published
release events generated by a user or an App/PAT.

The agent uses Aspire's existing bundle updater and verifier with the
released version, preserving archive hashes and publisher-attestation checks.
It compares the released inventory with the previous bundle, then assesses
the managed telemetry implementation and compatibility scripts. It must
propose a bundle-only PR when telemetry needs no changes.

PR publication uses a scoped GitHub App token, draft-only safe outputs, a
restricted file allowlist, and git-bundle transport for the binary archive.
The agent links an existing matching draft rather than overwriting it; a
closed, unmerged proposal requires a human decision. Older releases must not
downgrade the embedded bundle. The PR links its source release and commit;
the workflow never rewrites approved release notes.

### Prerequisites and rollout

Before enabling this flow on main:

1. Land Aspire-side ownership. Its bundle updater must stop copying telemetry
   scripts and recording upstream `hooks` provenance. Remove the metadata's
   `hooks` block and the cross-repository hook-byte enforcement. Keep archive
   hashes and publisher-attestation verification, including compatibility with
   releases produced by the current `publish.yml`.
2. Remove Aspire's `.github/workflows/update-aspire-skills-bundle.yml` so two
   automations cannot compete. Remove the synchronization-only hook branch
   restriction and update any required-check configuration.
3. Make `ASPIRE_BOT_APP_ID` and `ASPIRE_BOT_PRIVATE_KEY` available to this
   repository. The App installation must cover `aspire-skills` and `aspire`,
   with contents, issues, and pull requests read on both repositories and
   write on Aspire for safe outputs and maintenance. Checkouts and repository
   tools use read-only tokens.
   Enable Copilot-powered agentic workflows under the organization's policy.
4. Exercise a known release and a rerun, inspect the draft's bundle and
   telemetry changes, and complete the required Aspire review.

An inline preflight fails while Aspire still has the old ownership metadata
or standalone updater. Ensure the release asset is uploaded before publishing
the release. Rerun the existing GitHub Actions run to retry an update; its
release tag and commit remain fixed.

Keep the canonical hooks and their packaging here until the Aspire-side
ownership change and replacement workflow have been verified. Inventory any
unpropagated behavior changes before removing those sources. Removing the
compatibility scripts from Aspire is not part of this migration.

Release notes and released files are treated as evidence, not executable
instructions.

### Agentic workflow maintenance

Use the compiler version recorded in the generated workflow headers
(`v0.89.17`). Compile on Linux or WSL: this compiler's
Windows build fails secret-redaction path validation. Regenerate instead of
editing generated YAML:

```shell
gh aw compile --purge --validate --no-check-update --schedule-seed microsoft/aspire-skills
gh aw lint --shellcheck
```

Commit `.github/workflows/update-aspire.lock.yml`,
`.github/workflows/agentics-maintenance-microsoft-aspire.yml`,
`.github/aw/actions-lock.json`, and the generated `.gitattributes` declaration
with source changes. The compiler's maintenance workflow has only manual and
reusable-workflow triggers; privileged operations require a maintainer check.
It does not schedule updates or merge PRs. Regenerate and lint the workflows
locally when changing their source.
